| `group.overview/joins` | 目标公开的小组信息 | 各 1 页样本；身份仍由目标路径与 profile 取证，导航只说明操作者。样本有限。 |

“公开抓取”不等于“整张 HTML 只包含目标内容”。账号列表、长文等仍按已绑定的操作者访问，
原始 WARC 可能包含导航、回复、社区内容；它是页面证据，不能直接作为已过滤的公开站点发布。
此次不修改历史 WARC。公开作品目录改为无凭据请求，是减少原始页面中无关个人评价的一道防线，
并不保证豆瓣返回页没有社区评论或其他上下文。派生输出继续依赖各内容容器/作者过滤。

## 恢复与回归

请求策略在每次 `_fetchOne` 根据已锁定运行视角和路线重新决定，不依赖新增 checkpoint 字段。
因此旧断点中已排队的目录 URL 冷恢复后同样无凭据；manifest 的操作者仍记录原操作者。
目录返回退出登录导航不再误报操作者退出；豁免只作用于该响应，下一张账号页面仍检查换号/退出，
恢复前的目标和操作者握手保持原规则。异常目录响应若仍显示登录者，记为 `unknown` 并停止，
保留证据但禁止解析摄取。不因验证码或限流失败自动换身份重试。

测试覆盖首次/冷恢复的五类作品 URL、本人目录、异常登录响应、后续账号页换号/退出、
重定向无凭据、ck 拒绝、最小间隔与退避，以及详情控件对 canonical 的隔离。

## Chrome 开始消息回归

在独立 Chromium 扩展环境使用模拟豆瓣响应复现：查看 `154611037` 成功，开始时出现
`The message port closed before a response was received.`。原因是 `start.target` 的账号对象
被后台 `if (msg.target) return` 当作离屏地址丢弃；现仅排除 `OFFSCREEN_TARGET` 字符串。
另修正冷启动竞态：离屏文档存在不代表模块监听器就绪；先以有界 ping 握手等待，再发一次写命令。
不会自动重发 start。Node 测试执行真正后台监听器，浏览器验证实际跨上下文消息链路。

最终验证：扩展 `npm test` 2,061 通过、0 失败、1 个既有跳过；解析器 307 通过、
0 失败、1 个既有跳过。vendor 逐字节校验包含在测试中。Chromium 156 独立测试档案中，
模拟豆瓣响应，经真实 service worker/offscreen/OPFS 消息链路，公开目标开始成功，
随后本人开始成功；没有使用真实豆瓣 Cookie 或发起实网抓取。

## 2026-10-15：真实第三方 bundle 补验

本地 `~/downloads/exports_3rd` 中一份抓取途中跨过多次修复的 bundle；此节使用真实
「登录 B 抓 A」的原始响应，补充前文只有历史本人样本的边界。原始档案只读，未重写
索引、WARC 或 manifest，也未将 HTML、会话信息和正文提交到仓库。

- 565 次捕获，2 个 WARC 段：560 次原判 `ok`、4 次 `challenge`、1 次 `unknown`。
  `doubak-data-parser/bin/verify.js` 的段摘要、索引摘要与逐捕获完整性检查通过；
  `bundle/v1/validate.py` 在安装 jsonschema/referencing 的环境中通过完整校验。
- 114 个 HTML 响应用 PR #24 的当前分类器、各自路线和 `visibility: public` 复判，
  全部为 `ok`。变化恰好是上述 5 次历史失败：4 张主页受旧脚本验证码文案误判影响，
  日记是此前不认识的第三方空列表。这里验证的是保存的正文与 URL/status，未重放
  当时的滚动体积基线或网络状态。
- 日记在当地时间 18:49:19 有后续 `ok` 空列表，最终 `note.list` 连续且无缺口；
  主页在 21:18:21 有后续 `ok`。旧索引保留原判定是正确的追加式历史。
  **主页的最终覆盖声明仍有旧版留下的 4 个无 URL `challenge` 缺口，contiguous=false。**
  这是旧 `markStopped` 写法的遗留；新版本按确切 URL 修复缺口不会猜测性清除无 URL
  缺口，也不追改已经收尾的 manifest。`status: complete` 不等于每条路线连续性均已证明。
- 影视「看过」标题声称 360，实际获取 355 个不同作品。start=0..345 每隔 15 的页面
  都在，360/375 是空终止页；75、135、270 的原始 HTML 分别只有 13、13、14 个
  `item comment-item` 容器及相同数量的作品 ID，正好少 5 个。不是漏抓分页或解析器
  丢掉页面中已有条目；不能从这些字节进一步断言未展示条目被删除、私密或被审查。
- 广播页面共 464 个 status-item 出现次数、463 个不同 ID；其中 2 个是转发嵌套的
  其他作者，目标自己的 462 次出现去重后为 461 条。canonical 恰为 461 条，未将
  两个其他作者的广播认领给目标。coverage 的 463 计数来自页面 ID 集合，不能直接
  当作「目标本人发布数」，完整转发关系模型仍属于设计中尚未完成的内容。
- 所有带 `/people/` 路径的 HTML 请求都指向目标；114 页的导航 UID 均为操作者，
  与 manifest 的目标 UID 不同。这是原始页面的访问者上下文，不应被说成导航已脱敏。
  canonical 中 917 条有账号归属的记录全部属于目标，1,366 个观测的
  `absence_authority` 均为 `none`。本份开启 `skip_catalog`，没有作品详情 HTML，
  **不能据此宣称实际网络环境中的匿名作品详情隔离已验过**。
- 离线解析无告警：标记 448、作品 448、广播 461、长文 2、豆列 2、加入小组 4；
  相册与小组话题均为 0。全部 canonical schema 校验通过。

档案页的「有 5 条没能正常抓到」统计历史失败捕获次数，不是 5 个当前仍缺失的页面；
此次只有两个不同 URL，且都有后来成功的响应。「页面结构变了，重抓没用」也只是当时
缺框架标志的通用解释，不应当作在修复分类器以后仍不能成功的结论。

## 2026-10-16：本人增量与 topic 广播回放

对 `20261015T140553Z-bdbdd1`（315 条捕获）及本地保存的 `broadcast p1 failed.html`
做离线核对，未访问豆瓣、未改写原 bundle 或样张站：

- 广播正文的链接标题引用了「页面不存在」。分类器原来全文匹配，将正常第一页判为
  `soft404`。该判定表示资源不存在，frontier 会结束条目而非重试；因此输入方式、重抓
  都不能改变结果。现在只识别错误页的 `title` / `h1`，真实错误页仍保留原有语义。
- 本人数字主页没有重定向，但资料区头像链接给出了原自定义域名。原实现直接使用
  最终 URL 的数字路径，导致 `previous_bundle_id` 与所有 `floor_time` 为空。这次
  实际是全量枚举。现在仅从目标资料区头像链接识别域名，开始前核对 UID，仍按
  UID、域名、视角与公开操作者隔离基准，不放宽不同自定义域名间的链匹配。
- 修复后识别到 `20261011T113553Z-6dd948`。用实际捕获响应回放电影 collect 路线，
  从本次全量的 93 页降至 1 页，保留该基准下界与连续性声明。
- 升级前使用数字地址的断点保留原地址；新增本人数字入口、显式网址、冷/热恢复测试，
  原有跨账号、跨操作者及自定义域名变化拒绝测试仍通过。
- topic 动态的 `data-sid` 与 `data-aid` 不同：身份保留 sid，独立标题写入 canonical
  `fields.title`，标题链接写入 `url`；不把 topic 冒充作品标记或作品卡片。站点保留
  时间锚点，另显标题并支持标题搜索。公开测试使用不含真人内容的缩小结构夹具。
- 原始及另存 HTML 均重新判为 `ok`。仅在临时内存视图中重判那一条历史索引，解析出
  20 条广播，canonical 全量 schema 校验、四种导出逐字段检查通过；Chromium 离线
  检查确认标题、原页链接、时间锚点与搜索跳转正常。正常 parser 仍尊重历史索引 verdict，
  不会自动把旧 `soft404` 改为成功；重新抓取的成功捕获才作为正式的新观测。
