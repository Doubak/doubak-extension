# 界面设计

> 草案 v0.1（2026-07-29）。补 DESIGN.md §4-K 留下的空白——那里只有四行功能表，
> 不足以指导实现。本文定义**界面长什么样、说什么话**，不定义实现技术。

## 0. 三个约束决定了一切

**① 状态不在内存里。** MV3 的 service worker 随时会被杀；面板一关，它的
JS 就没了。所以界面**不是状态的持有者，只是状态的视图**——所有进度、队列、
断点都活在 IndexedDB，界面每次打开都重新读。这不是实现细节，它决定了界面
不能有「只在这个页面开着时才成立」的东西。

**② 抓取是几小时起步的长任务。** 用户会关掉标签页、合上笔记本、第二天再来。
界面必须能回答「我上次抓到哪了」，而不是只显示当下这一刻。

**③ 计数不可信，所以进度条会撒谎。** 这是最容易做错的一处，单列一节（§4）。

## 1. 界面构成

| 界面 | 用途 | 为什么是它 |
|---|---|---|
| **主面板**（独立标签页） | 唯一的工作区：范围、进度、覆盖率、日志、档案、导出 | 长任务要盯几个小时，得是个不会自己关掉的地方 |
| **存储页**（主面板的一个标签） | 用量、bundle 列表、导入导出、删除 | 档案体量可达数 GB，值得有自己的地方。**它一度挂在调试页下面**——而调试页里全是会改变抓取行为的东西（演练、绕过门控、小范围试跑），把一件日常操作摆在那儿，等于训练用户往那儿去找东西 |
| **档案页**也能删当前这一份 | 删除 | **那里才有上下文**：你刚看过它有多少条、多大、导出过没有。存储页那份是批量视角，两个都要 |
| **系统通知 + 角标** | 需要人工介入时把用户叫回来 | 用户不会一直盯着面板 |

点工具栏图标直接开主面板；已经开着就切过去，不再开一个。

### 1.1 popup 拆掉了

原本这里还有一个 popup：状态、开始/暂停，外加一个「打开完整面板」按钮。做出来之后
它一直是个**多余的中间层**——

- 真正要看的东西一个都放不下：日志、覆盖率对账、档案预览、抓不下来的页面。
- 它**一失焦就关**。而这个工具的核心场景是「盯着一个跑几小时的任务」。
- 实际用法从来都是「点图标 → 再点一下进面板」。那不如直接去面板。

留下来的成本也不只是多一个文件：状态要在两处渲染、两处都会撒谎、两处都得测，而
`Exclusive`（F-04i）挡的头号并发场景「popup 和面板都点了开始」根本就是它自己造出来的。

**实现上有个坑**：manifest 里只要还留着 `default_popup`，`chrome.action.onClicked`
就**永远不会触发**——点图标会变成什么都不发生。两者是互斥的，`test/manifest.test.js`
钉住了这一点。

## 2. 首次使用

开抓之前必须过一次说明页，这不是欢迎页，是**知情同意**（F-01d）：

```
┌─────────────────────────────────────────────┐
│  开始之前，请了解这几件事                      │
│                                             │
│  · 所有请求都来自你自己的浏览器和 IP，          │
│    用你自己的登录状态。                        │
│  · 你的 cookie 和密码不会发送到任何地方，       │
│    包括我们。                                 │
│  · 抓取速度是刻意放慢的。豆瓣如果要求验证，      │
│    插件会停下来等你处理，不会自己重试。          │
│  · 抓取可能持续数小时。中途可以随时暂停，        │
│    进度不会丢。                               │
│                                             │
│  [ 我明白了，继续 ]                           │
└─────────────────────────────────────────────┘
```

措辞刻意平实。这批用户里有人的账号一旦被封就再也拿不回来（注册手机号已停用、
短信验证过不去），把风险说清楚比让界面显得轻松重要。

## 3. 主面板

五个标签页：**概览 / 范围 / 覆盖率 / 日志 / 存储**。

### 3.1 概览

```
┌───────────────────────────────────────────────────────────┐
│  正在抓取 · 账号 mewcatcher                    [ 暂停 ]     │
│                                                           │
│  广播          ████████████░░░░░  已抓 1,842 条            │
│                已回溯到 2023-04-12 · 还剩约 1 年 4 个月     │
│  日记          ✔ 完成 · 37 篇 · 连续性已验证                │
│  影评书评      ✔ 完成 · 112 篇 · 连续性已验证               │
│  相册          等待中                                      │
│  标记（电影）  等待中                                      │
│  作品详情页    等待中 · 需先完成广播                        │
│                                                           │
│  已用时 1 小时 12 分 · 当前速度 约 4 秒/页                  │
└───────────────────────────────────────────────────────────┘
```

要点：

- **每条路线一行**，状态一目了然。
- 「作品详情页」显式写出**为什么**在等（前置依赖 F-03k），否则用户会以为卡住了。
- 「连续性已验证」是**唯一**能说的完整性判断，措辞就用这个，不说「已全部备份」。
- 速度显示出来，因为它会随退避变慢——用户看到变慢时应当知道这是设计如此。

### 3.1.1 抓完之后不清空进度表

抓完立刻变回「还没有开始」，等于把刚跑完那一次的结果扔了——而那正是用户此刻最想看的
东西。

显示的数据取自**最新那份档案的 `manifest.crawl_state` + `coverage`**，而不是内存里的
快照：manifest 是权威记录，而 runner 一收尾内存就清空了。顺带这也让「重开面板还能看到
上次结果」成立。

「已回溯到」用 `low_water_time`（区间的最旧那一端）。那是为此加进规范的可选字段
（bundle/v1 §5.4.1.1）——之前只持久化了水位线（最新那端），所以抓完之后说不出
「这次覆盖了 2023-02-04 → 2025-05-05」。

### 3.2 范围

勾选要抓哪些路线族。默认全选，但：

- **广播永远在最上面**，并且默认不可取消勾选（可以改，但要多一次确认）。它是唯一
  真正紧急的东西：不可编辑、可静默删除。
- 首次抓取可以设一个**起始日期**（只抓这个日期之后的）。默认不设，即抓到最早。
- **作品详情页单独一栏**，并如实标注体量：

  ```
  ☑ 作品详情页（电影/书籍等的条目页）
     生成静态网站需要它。但它占档案体积的九成左右，
     可以之后单独删除而不影响你自己写的内容。
  ```

### 3.3 覆盖率 —— 这一页最容易做错

见 §4。

### 3.3.1 「在看哪份档案」只能有一个所有者

覆盖率原来有**两条渲染路径**：档案页 `openBundle()` 的副作用，以及覆盖率页自己的加载器。
两个真相来源，症状有三个：

- 没去过档案页时，覆盖率页与档案页可能不是同一份档案
- 删掉档案之后，选中的 id 还指着一个不存在的目录 → 下次读取报「读不出来」，而真实情况
  只是它被删了
- 抓完一次之后，缓存没人让它失效

现在只有一处知道「在看哪份、它的摘要是什么」（`loadBundleSummary` + `summaryCache`），
两个标签页都从那里读，而**任何会改变存储的动作都调 `invalidateBundles()`**：删除单份、
清空全部、抓取开始、抓取收尾。

作废之后还要**重画当前打开的那一页**（`refreshOpenTab`）。只作废不重画的话，用户会盯着
一份已经被删掉的档案的数字。

覆盖率页顶上写明是哪一份档案——档案页有下拉可以切换，不写出来的话两页对不上时没人知道
自己在看什么。

### 3.3.2 每个要读档案的页面都得有加载态

覆盖率页原来**没有自己的加载**：它只是档案页 `openBundle()` 的副作用，所以第一次直接
点进覆盖率是空白的，要先去过档案页才有东西。

而**空白看起来像「正在加载」**——用户会等，而实际上什么都不会发生。读 OPFS 要经过
Worker、是异步的，所以先说「正在读取档案…」，再说结果（包括「还没收尾，覆盖率证据是
收尾时才攒的」这种情况）。

### 3.4 日志

时间倒序，可按级别过滤，可导出。**导出前必须脱敏**（F-11d）：日志里会有
URL、用户名，诊断包不能原样发给别人。导出按钮旁边直接写明这一点。

日志**存在本机的 IndexedDB 里**，最多 500 条，重开还在。原来它是个内存数组：只记面板
打开期间的事件，一刷新就没——而界面上却写着「仅本地保留…导出前请自行脱敏」，那句话同时
暗示了「存下来了」和「有导出」，**两个都不存在**。承诺要么兑现要么改掉，这里选择兑现。

**只记 `index.ndjson` 里没有的事件**：重试、停机、错误、门控放开、暂停。每一次成功的
捕获那边已经逐条记了，而且更权威（带偏移量与摘要）；抄一遍只会得到两份可能不一致的记录，
还把真正稀少的信号淹掉。

一条只留人看得懂的字段（时间、类型、路线、原因、URL、错误信息），**不留整个事件对象**：
里面可能有大段 HTML 或错误栈，而日志有条数上限没有字节上限——一条超大记录会把有用的挤掉。
错误信息截到 500 字符，URL 截到 300。

有「复制日志」，剪贴板被挡时退回到一个 textarea 手动全选。导出文本开头就写明里面有 URL
与用户名——它是本地诊断工具，不是可以随手贴到公开地方的东西。

见 §6。

## 4. 进度与覆盖率：不能给用户假的安心

这一节是整个界面里最重要的约束，来自一个实测事实：**豆瓣的计数不可信**——
它有时统计于审查之前、有时之后。同一次抓取里电影分毫不差，游戏差 5 条。

由此三条硬规则：

### 4.1 不用「豆瓣声称的总数」当进度条分母

前代工具就是这么干的（`this.total = statuses_count`）。分母不可信，百分比就
不可信，而百分比看起来又特别可信——这是最坏的组合。

**改用两种诚实的进度表达：**

| 路线类型 | 怎么显示 |
|---|---|
| 有时间边界的（广播） | **回溯到的日期** —— 「已回溯到 2023-04-12」。用户天然懂这个，而且它是**真的** |
| 全量枚举的（标记列表） | **绝对条数 + 当前页码** —— 「已抓 1,842 条，第 62 页」 |

百分比只在能明确标注为估算时使用，且必须带「约」字。

### 4.2 覆盖率页面说事实，不下判断

```
┌────────────────────────────────────────────────────────────┐
│  覆盖率对账                                                  │
│                                                            │
│  ⓘ 豆瓣页面上的条目数量【不能】用来判断备份是否完整。          │
│    豆瓣有多套内容屏蔽机制，它的计数有时统计于屏蔽之前、        │
│    有时之后。下表的差值是【线索】，不是错误。                  │
│                                                            │
│  路线            豆瓣声称   实际抓到   差值   连续性          │
│  ─────────────────────────────────────────────────────     │
│  电影 / 看过       1,157     1,157      0    ✔ 已验证        │
│  电影 / 想看         627       627      0    ✔ 已验证        │
│  游戏 / 玩过         293       288     −5    ✔ 已验证        │
│  广播                 —      2,839      —    ✔ 已验证        │
│                                                            │
│  ⓘ 游戏这类差值通常意味着有条目被豆瓣隐藏了——它的计数器      │
│    知道这些条目存在，但列表里不显示。你的备份本身是连续的。     │
└────────────────────────────────────────────────────────────┘
```

关键：

- 差值列**不用红色**，不加感叹号，不写「缺失」。它不是错误。
- **完整性看「连续性」那一列**，不看差值。这是唯一有效的判断。
- 广播的「豆瓣声称」显示 `—` 而不是 `0`。**null 与 0 是两件事**，界面上也必须分开。
- 差值非零时给出**最可能的解释**，避免用户以为是插件出了 bug。

### 4.3 有缺口时必须说出来

连续性验证不通过时，不能只显示一个叉。要说清楚缺在哪、能不能补：

```
⚠ 广播 · 连续性未验证
  2023-08-14 到 2023-08-16 之间有一段没抓到（3 页失败）。
  这段区间的内容可能不完整。
  [ 重试这一段 ]
```

### 4.3.1 「已回溯到」用的是最旧那条，不是水位线

抓取从新往旧走，所以：

| | 是什么 | 谁要看 |
|---|---|---|
| `newestSeen`（水位线） | 本次最新的一条 | **下次抓取**（当下界） |
| `oldestSeen` | 本次最旧的一条 | **用户**（当进度） |

界面原来显示的是水位线。而列表是新→旧，它在第一页就定住了、之后永远不动——于是抓了
十页那个日期一动不动，看起来像卡住了。（被当成 bug 报过来一次。）

进度必须用 `oldestSeen`：每往回翻一页它就前进一点，那才是「已回溯到」这句话的意思。

两个值都留着，因为它们回答的是两个不同的问题。判断「水位线能不能推进」用的仍然是
`newestSeen`。

### 4.4 `active` 不等于「正在发请求」

抓取停下来之后仍然「在内存里」——那样才能继续。所以状态里有两个不同的东西：

| 字段 | 意思 |
|---|---|
| `active` | 这次抓取还在内存里，可以继续 |
| `stopped` / `stoppedBy` | 已经不发请求了，以及为什么 |

界面把它们混为一谈过一次，后果是**暂停之后依旧显示「正在抓取」**，用户以为按钮没
生效然后反复去点。

还有一条：暂停要**立刻给反馈**。一批最长 22 秒，期间不给任何回应的话按钮看起来就是
坏的。所以点下去先显示「正在暂停…（当前这一页抓完就停，不会丢东西）」。

同一个混淆在**继续**那一侧咬得更狠：`resume()` 见到 `active` 就当成「已经在跑了」
直接返回，于是「继续」什么也没做，下一批立刻又报同一个停机原因，界面弹出「需要你
处理：你手动暂停了抓取」——用户点继续，得到的是同一条通知。完整的三层成因见
DESIGN 的 F-10b2。

### 4.4b 一行「正在抓 …」

「档案 20260730T130118Z-a60b6a · 当前间隔 1.0 秒」在几个小时里几乎一动不动。它没有
说谎，但也没有回答用户唯一想知道的问题：**它到底还在动吗**。

所以状态里加一行当前 URL（去掉 `https://`，够长了）。两批之间没有在飞的条目，那时候
退回「刚抓完 X」——这一行要是时有时无，就变成了新的闪烁源，而「进度区每几秒闪一下」
正是被报过来的老问题。措辞跟着状态走：`currentActive` 决定说「正在抓」还是「刚抓完」，
两者不是一回事。

同一个 URL 也进日志（F-11d）。事后排查「停在哪一页」时，只有 `routeKey` 是答不出来的。

### 4.4c 空闲态的进度表归「上一次结果」管

抓完之后立刻把进度表变回「还没有开始」，等于把刚跑完那一次的结果扔了——而那正是
用户此刻最想看的东西。所以空闲时显示上一份档案的 `crawl_state`（写在 manifest 里的
**权威记录**，比内存里的快照可信）。

#### 「连续性」那一列：说结论，不说我们对自己的信心

这一列改过三版，每一版都是被同一个问题咬出来的：**它说的到底是「档案怎么样」
还是「我们查得怎么样」？**

| 版本 | 毛病 |
|---|---|
| 「进行中」 | 抓完的档案里也这么写——叫人一直等一件已经结束的事 |
| 「未验证 · 有缺口」 | 「未验证」听起来像**我们的代码没查**，而其实查了，结论就是有缺口 |
| **「有 N 处缺口」** | 说的是档案本身的结论 |

**不能写「已验证 · 有缺口」**（用户提过这个建议，值得记下为什么不采纳）：
「已验证」在这个项目里有确切含义——连续性证明成立，也就是「这条线以上全都抓到了」。
有缺口时它不成立。两个词并排放，读快一点就会看成「验证通过」，而**假的完整性
声明是这个项目最不能出的错**。宁可措辞笨一点。

四种结论：`✔ 已验证` / `进行中` / `有 N 处缺口` / `没走完`（最后一种是「没到下界、
也没停滞终止」，不是有洞）。覆盖率页走同一个函数，同一件事不能在两个页面上说成两样。

**踩过的坑**：空闲分支末尾原来无条件 `renderRoutes([])`。第一次进空闲时它先清空、
随后异步的 `showLastRun()` 把表填上——看起来是对的；但轮询每两秒来一次，那时
`showLastRun()` 因为已经跑过而不再跑，这一句却照常执行，**于是刚显示出来的表在几秒
后被抹掉**。用户看到的是：打开插件先看到完整的上次结果，几秒后整块空了。

规则写清楚：**空闲态下这张表只有 `showLastRun()` 能写**，其余地方一律不碰。
唯一的例外是刚从「抓取中」进入空闲的那一次——那时要先清掉抓取期间的残留，再让位。

### 4.4d 「正在做什么」由做事的那一端报出来

开工要先确认账号：抓一次个人主页取数字用户 ID 并确认登录状态，两次真实请求、
要过节奏闸门，可能好几秒。**这段时间既没有 runner 也没有 checkpoint**，照着状态
渲染就只能说「没有进行中的抓取」——而用户刚点了开始。

第一版的做法是点下去先本地 `setState('run', '正在确认账号…')`。那是**界面自己编的
状态**，两个毛病：

1. 两秒一次的轮询读到真实状态之后立刻把它盖掉。用户看到的是
   「正在确认账号…」→「没有进行中的抓取」→（很久之后）「正在抓取」。
2. 它活不过面板刷新——换个标签页回来就什么都看不到了。

正确的做法是让状态从**做事的那一端**来：全局互斥锁（F-04i）的持有者本来就知道
现在在干什么，把它一路带到界面（`offscreen → background → panel`）。界面只是读它，
不发明它。这与 §0 的第一条约束是同一件事：状态不在内存里。

界面**只保留开口那一小段的兜底**：从点下去到 offscreen 真正拿到锁之间（可能还要先
把 offscreen 建起来），后端还报不出来。一旦报得出来就以后端为准。

**这个判断必须在所有分支之前。** 第一版只放在空闲分支里，于是「有 checkpoint、
点继续」时走的是另一条分支，界面照旧渲染「抓取已停下」——点下去到几秒后之间一动
不动，然后忽然全出来。而恢复本来就慢（修段尾 + 确认登录状态，都是真请求），那几秒
最需要交代。

配套规矩：忙碌期间不给「开始抓取」按钮——按了也只会撞上互斥锁，得到一句
「已经有一个在跑」。另外每个会占锁的操作都必须在界面上有对应的说法，
`test/offscreen.test.js` 会逐个核对；漏一个就会退回「没有进行中的抓取」。

### 4.4e 「已回溯到」用每页的中位数，不用全局最小值

进度不能用百分比（§4.1），所以显示「已回溯到某日」。第一版用的是水位线（最新的
一条），而列表是新→旧，那个值在第一页就定住了——抓了十页日期一动不动。改用
「本次最旧的一条」之后，撞上了第二个坑：

**一条离群的旧条目就能把它永久钉死。** 真实数据里，一份 20 页、严格新→旧的广播
列表，唯独第 10 页混着一条 2018 年的：

```
第 9 页  → 2025-12-09
第 10 页 → 2018-08-18   ← 离群
第 11 页 → 2025-08-29
```

从第 10 页起界面上就一直是 2018-08-18，再也不动。那个值**没说谎**（我们确实抓到
了一条 2018 的），只是它回答的不是「抓到哪儿了」。

所以分成两个量，各回答各的问题：

| 量 | 是什么 | 用在哪 |
|---|---|---|
| `low_water_time` | 全局最小值 | manifest；抓完之后「这份档案往回覆盖到 X」 |
| `progressTime` | 每页中位数的累计最小值 | 界面上抓取期间的「已回溯到」 |

中位数是因为**一条离群值动不了它**；累计取最小是因为**进度只能往前不能回头**——
来回跳比不动更让人不安。

### 4.4f 「豆瓣上已经没有了」的那几条要单独列出来

一份 3347 条的真实档案里有 8 条 `gone`——那 8 部电影豆瓣已经删了，网上再也查不到，
而档案里存着它们当时的样子。**那是整份档案里最不可替代的信息**，也正是这个项目
存在的理由本身。

而它原来只以「判定分布：正常 3339 · 已不存在 8」这一个数字出现，**没有任何地方
说得出是哪 8 条**。捕获列表里理论上能看到，但那一栏只渲染前 500 行，而它们排在
第 3000 多条——根本画不出来。

所以档案页单独给它们一块地方，列出 URL 与抓取时刻。同样列 `blocked` / `challenge`
/ 判不出来的：都是稀少而要紧的痕迹。

**日志那边是同一个问题的另一面。** 抓取环只有 200 条（每页一条），而这次抓了
3347 页，于是 8 条 `gone` 里**只有最后一条**留了下来。判定不是 ok 的捕获现在改走
稀疏环（500 条，专为「稀少且要紧」准备的那个）——它们本来就属于那里。

### 4.5b 抓取方式让用户选，默认帮他省时间

三个选项，默认第一个：

| 选项 | 什么时候用 |
|---|---|
| **增量（推荐）** | 接着上次抓：列表只抓新增的，作品详情页只抓这次新出现的 |
| **全量重抓** | 上一次有缺口、或者你不信任它——重新打一份基准 |
| **增量 + 重抓作品详情页** | 评分、短评这些会变的东西想拿到新版本时 |

**默认增量、但必须能选。** 静默地帮用户做决定，在「这次到底抓了什么」这件事上是
不能接受的——尤其当默认行为会**跳过**东西的时候。第三个选项存在的理由也在这儿：
作品详情页占九成体积，默认跳过是对的，但「我就是想看评分变了没有」是个正当需求。

### 4.6 链：增量之后，单份档案的数字不再说明完整性

一旦接上增量，一份档案的「实抓 3 条」可能完全正常——它只是这次新增的部分。
**完整性是整条链的属性**，所以链必须在界面上看得见，而不是藏在 manifest 里。

设计见 DESIGN.md §3.3b 与规范 §5.5。界面这一侧要做三件事：

#### 覆盖率页：两个视角，默认「合起来」

```
合起来 · 3 份档案                          [ 这一份 ]

广播          2014-01-10 ─────────── 2026-08-15   连续 · 跨 3 份
电影 · 看过    2014-01-10 ─────────── 2026-08-15   连续 · 跨 2 份
作品详情页     —                                   不适用（无时间锚）
```

主角是**连续区间**，不是数字。**刻意不算「合起来一共抓了多少」再跟豆瓣声称的比**：
边界是闭区间去重、必然重叠，那个数只会误导；而这一页存在的全部理由就是
「计数不能证明完整性，连续性才能」。声称数量仍然显示（取最新一次观测），只作线索。

**一堆档案不等于一条链。** `previous_bundle_id` 为 null 的那些各自是一条链的起点——
增量做出来之前的每一次抓取都是独立全量。第一版把它们全接了起来，真实数据上的样子是
「合起来 4 份档案，从最近的一份往回接」，而且**每一行都变成了「没走完」**：最差那
一份污染了全部，包括那些各自明明验证通过的。这一页只讲最新那一条链，不在链上的
另外说一句（不提的话看起来像档案丢了）。

链断了的时候（基准被删了）要**明说**，并且不能因此把在场的那几份说成无效：

> 广播的链在 2026-08-15 那一份断了：它的下界指向档案 `…d8e1b2`，而那份已经不在了。
> 在场的这几份各自抓到的东西都还有效，只是「从今天连续回溯到 2014-01-10」这句话
> 现在证明不了。

#### 档案页：差异要看得见（已实现）

- 增量档案顶部直说「接在档案 xxx 后面」——它的「捕获条数」只含新增的部分，
  不说清的话看起来像抓漏了
- 「这一份里 N 条是新增的，M 条是又抓了一次」，并就地给列表补标
- 按 `url_key` 聚出**版本历史**：「3 个版本：07-31 / 08-15 / 09-02」

**「又抓了一次」不是浪费，也不是重复数据。** 下界比较是闭区间（宁可重复，不可
遗漏），边界那一段必然重叠；而同一个网址在不同时间的内容**可能真的不一样**——
评分变了、短评改了、条目被删了。那是版本，不是冗余。这也正是为什么不能靠复制
基准来「保证」链完整（§5.5.4）：复制会把两个版本压成同一份数据的两份拷贝。

全都**只读 index，不解压任何记录**——这两个问题的答案全在 index 里，而一份真实
档案有 3347 条，解压是几秒钟的事。

#### 导出：「这一份」与「整条链」

增量之后，**一份档案不再是一份完整的备份**——它只含新增的部分。要把「我的豆瓣」
整个搬走，需要的是整条链。让用户自己一份份导，早晚会漏掉一份，而漏掉哪一份是事后
看不出来的。

整条链**必须导进各自的子目录**（`doubak-bundle-<编号>`，与 OPFS 里同名，搬回来时
不用改名）。平铺的话每份的 `manifest.json` 与 `README.txt` 会互相覆盖——这不是
理论问题：真实使用中用户的下载目录里就只剩了最后一次导出的 manifest，早先几份的
全被盖掉，以至于事后想核对哪份接在哪份后面都做不到。

两条与单份导出一致的规矩：**只在校验通过时才记「已导出」**（没验过就说导出了，等于
给一个我们没资格给的保证，而删除确认框会据此决定说得多重）；**一份失败不中断其余**
（用户要的是尽可能多地搬走，而不是在第三份上停下、前两份还不知道成没成）。结果逐份
列出，不汇总成一句「成功」。

#### 删除：警告，不阻止

删一份被引用的档案时说清后果（「这份是 N 份增量的基准，删了之后那几份的广播就
断链了」），但**不阻止**——那是用户的档案。存储页显示引用计数。

### 4.4g 暂停 ≠ 中止

| | 语义 | 之后能删吗 |
|---|---|---|
| **暂停** | 等会儿接着抓 | **不能**——档案还在写，指针还指着它 |
| **中止** | 这次到此为止 | 能。收尾成 `aborted`（如实带上缺口），放开指针 |

存储页原来那句「这份正在抓，先暂停或等它结束」**是错的**：暂停之后它依旧删不掉，
用户照做一遍会发现什么都没变。现在那句话指向「中止」。

确认框要说清**不可逆的是什么**：

> 档案 xxx 已经抓到的 N 项都会留下，可以照常查看、导出。
> 但**这次抓取不能再继续了**——之后要接着抓只能重新开始一次
> （下次会是增量，只抓新增的部分，不会从头来）。
> 中止之后这份档案就可以删除了。

**不可逆的是这次抓取，不是数据。** 说反了的话，用户要么不敢按，要么按了之后才
发现丢了进度。最后那句「下次是增量」是关键的定心丸——没有它，「重新开始一次」
听起来像要再等几小时。

`checkpoint.json` **留在档案里**（规范 §3.1 要求 `aborted` 必须带），清掉的只是
我们自己那个「当前这次抓取」的指针。两者是不同的东西。

### 4.4h 每一块都要有自己的容器，**不许往兄弟节点里插**

`el.after(node)` / `insertAdjacentHTML` 插出来的节点**不属于任何一次渲染**——没有
哪段代码认为自己该清它。于是：

- 同一份档案刷新两次 → 两张一样的卡片
- 切换档案 → 上一份的卡片留在新档案上

真实现象：打开一份 05:13 的全量档案，上面挂着两张一模一样的「这是一次增量抓取，
接在 11:21 那份后面」。**一份 05:13 的档案不可能接在 11:21 后面**——那两张是看
别的档案时留下的。

规矩：每一块条件渲染的内容都有自己的 `<div id="…">`，渲染时 `replaceChildren()`，
切换档案时一并清空。`test/ui.test.js` 直接禁掉 `.after(` / `.before(` /
`insertAdjacent`。

### 4.5 通知只在状态**变化**时弹

心跳每 30 秒醒一次，每次都会重新判断「该不该恢复」。原来每次都弹一遍，于是同一件事
每半分钟糊到用户脸上一次——而它还带 `requireInteraction`，不会自己消失。

那不只是烦：**被通知轰炸的用户会去关掉通知权限**，然后连真正要紧的那条也收不到，
于是这个功能反而让「把人叫回来」这件事更难了。

去重状态要**存起来**（service worker 随时清零，内存里存不住），并且在问题解决时
**一起清掉**——不清的话，同一个原因第二次发生时会被当成「已经说过了」而不再提醒，
而那是一次全新的、真的需要人处理的事件。

角标不受这条限制：它本来就是常亮的兜底，重复设成同样的值没有代价。

## 5. 出问题时怎么说话

`pause_reason` 直接决定文案和可用动作。**每一种都要给出明确的下一步**，不能
只显示一个错误码。

| 原因 | 标题 | 说明与动作 |
|---|---|---|
| `challenge` | **豆瓣要求验证** | 「请在新标签页里完成验证，完成后回来点继续。插件和你共用登录状态，你验证完它就能接着抓。」<br>`[ 打开豆瓣 ]` `[ 我验证好了，继续 ]` |
| `blocked` | **豆瓣暂时限制了访问** | 「已经停下来了，不会重试——继续请求可能导致账号被限制。建议等待 30 分钟以上再继续，恢复后会自动放慢速度。」<br>`[ 稍后再说 ]` `[ 现在试试 ]` |
| `session_expired` | **登录状态已失效** | 「这不是错误，抓取已安全停下，进度都在。请重新登录豆瓣，然后回来继续。」<br>`[ 去登录 ]` `[ 我登录好了 ]` |
| `quota` | **存储空间不足** | 显示还需多少、当前用量，给出「导出并清理」的入口 |
| `crash` | **上次抓取被意外中断** | 「已从断点恢复，没有数据丢失。」——这条应当**安静**，不该吓人 |
| `user_paused` | 已暂停 | `[ 继续 ]` |

文案原则：

- **不说「错误」**。`challenge` 和 `blocked` 是正常的抓取过程，不是故障。
- **明确「不会自动重试」**。用户需要知道插件在保护他的账号，而不是卡住了。
- **恢复后降速这件事要讲出来**，否则用户会以为插件变慢了是 bug。

通知同理：角标显示 `!`，系统通知标题直接写要做什么（「豆瓣要求验证」），
而不是「Doubak 遇到问题」。

## 6. 存储页

```
┌────────────────────────────────────────────────────────────┐
│  存储                                                       │
│                                                            │
│  已用 3.2 GB · 可用约 47 GB       其中 1.1 GB 尚未导出       │
│                                                            │
│  档案                                                       │
│  ─────────────────────────────────────────────────────     │
│  2026-07-29 10:15   进行中   1.1 GB   [查看]                │
│  2026-06-01 08:30   已导出   2.1 GB   [导出] [删除]          │
│                     └ 其中作品详情页 1.9 GB  [仅删除详情页]   │
│                                                            │
│  [ 导入档案 ]  用于换机器后继续抓取                           │
└────────────────────────────────────────────────────────────┘
```

要点：

- **不要显示 `persist()` 的结果。** 实测（Chrome 151 / ChromeOS）：扩展里
  `navigator.storage.persist()` 恒返回 false，这是**预期行为**——扩展防驱逐靠的是
  manifest 的 `unlimitedStorage` 权限，Chrome 也从不为持久化存储弹窗询问。把这个
  false 展示成「未获保护」纯属吓唬用户，属于 §4 说的「制造假的确定性」的镜像错误：
  制造假的不确定性。
- **真正该显示的是「有多少还没导出」。** 见 §6.1。
- **「仅删除详情页」是一个真实按钮**：作品详情页单独成段（`catalog-*`），删除它
  只是删几个文件，不碰你自己写的内容。界面上要把这个区分讲清楚。
- 开抓前空间预检不足时，在这里而不是在概览页提示。

### 6.1 未导出的量要显眼

`unlimitedStorage` 文档上说能免于驱逐，但社区里确实有「装了这个权限、数据照样被
清掉」的报告。一场四小时的抓取如果**只有 OPFS 这一份**，赌的就是这个不确定性。

好在 bundle 是追加式分段的，所以有个更好的答案：**段一封就可以导出**，不必等整场
抓完。这样 OPFS 里始终只压着「当前这一段」，而不是四小时的全部成果。

界面上因此需要：

```
  本次抓取 1.1 GB · 其中 0.9 GB 已导出
  ⓘ 还有 3 个段没导出。段是封好一个就能导一个的，
    不用等抓完。                        [ 现在导出 ]
```

这比显示一个用户看不懂的 `persist(): false` 有用得多——它给的是**可执行的动作**，
而不是一个无从应对的警告。

## 7. 危险操作

| 操作 | 干预 |
|---|---|
| 删除**未导出**的档案 | 二次确认，且必须打字确认；说明「这份档案还没有导出过，删除后无法恢复」 |
| 删除已导出的档案 | 普通确认 |
| 取消勾选广播 | 提示它是唯一不可编辑、可被静默删除的内容 |
| 导出到已有文件的目录 | 不覆盖，改用新目录名 |

## 8. 状态怎么流到界面

```
service worker（抓取中）
   │  每抓完一页就写 IndexedDB
   ▼
IndexedDB ──────────► 主面板（打开时读，订阅变更）
   ▲
   └── 界面的操作（暂停/继续/改范围）也经由 service worker 落到这里
```

- 界面**只读状态、只发命令**，不直接改抓取状态。
- 面板打开时拉一次快照，之后订阅增量；关掉就什么都不留。
- service worker 被杀掉时界面应显示「正在恢复」，而不是「已停止」——这两者对
  用户意味着完全不同的事。

## 8.5 文案：书面语，且不是 Markdown

**两条规矩，都是被真实界面咬出来的。**

**① 界面文字是 `textContent`，不是 Markdown。** 写 `**强调**` 的话，星号会原封
不动地印在屏幕上。要强调就用 `<b>`。`test/ui.test.js` 直接扫可见文字与中文字符串
里的 `**`。

**② 用书面语。** 这是一个关于「档案能不能被信任」的工具，口语化的措辞会削弱它
本来要传达的确定性。对照：

| 口语 | 书面 |
|---|---|
| 又抓了一次 | 已抓取多次 |
| 这正是备份的意义 | 各个版本均予保留 |
| 已经停下来了，进度都在 | 抓取已停止，进度均已保留 |
| 不是重复数据，是版本 | 记录的是不同时刻的版本，并非冗余数据 |
| 你选的 | 已选择 |

**但不要因此丢掉信息。** 这些文案里最有价值的部分恰恰是「为什么」——
「重复抓取属于预期行为：下界采用闭区间比较（宁可重复，不可遗漏）」比
「存在重复记录」有用得多。书面化改的是语气，不是内容。

## 9. 文案原则

1. **中文**（F-11c）。面向用户的字符串一律中文。
2. **说人话**，不暴露内部术语。界面上不出现 `frontier`、`verdict`、`bundle`——
   对应说成「队列」「判定」「档案」。
3. **不制造假的确定性**。「连续性已验证」可以说，「已完整备份」不可以说。
4. **每个坏消息都带一个动作**。没有动作可给时，至少说清楚「不需要你做什么」。

## 10. 预览：这是信任功能，不是浏览功能

> **v0.2 修正。** 本文原先把「档案内容的浏览器内浏览」列为明确不做，理由是
> 「那是 site-generator 的事」。这个判断错了。

整个项目的承诺是**「你有一份完整的档案」**。而在有预览之前，用户没有任何办法
看到这件事是真的——他只能信。一份看不见的档案，价值全押在信任上，而这个项目
存在的理由恰恰是「不要把数据押在别人的信用上」。

所以预览要做，但它的定位是**验证**而不是**阅读**：

| 要做 | 不做 |
|---|---|
| 档案里有什么：条数、路线、判定分布 | 好看的作品页、条目详情渲染 |
| 「验一验」按钮：顺着 index 把每条记录取出来解压 | 全文搜索、筛选、排序 |
| 单条捕获的原始内容（HTML 源码 / 图片 / JSON） | 把档案渲染成一个站 |
| 覆盖率与连续性证明 | 编辑、标注、补录 |

**边界**：预览**只读**，绝不写任何东西，也不建索引缓存。档案本身就是真相；
再存一份派生状态就会有两个可能不一致的来源——那正是「任何东西都不写投影」
这条规矩要防的事。

把档案渲染成一个可浏览的站，仍然是 site-generator 的事。这里做的是「让你确认
抓到了什么」，两件事的产物和生命周期都不一样。

### 10.1 捕获列表每行必须说得出信息

原来一行只有路线名与判定，于是列表长成一串「广播 正常 / 广播 正常 / 广播 正常」——
除了顺序之外什么信息都没有。而档案页存在的意义恰恰是**在档案里找东西**。

每行四样，全部来自 `index.ndjson`，**不解压任何记录**：

| | 从哪来 | 回答什么 |
|---|---|---|
| 路线 · 第几页 | `route_key` / `cursor` | 这是哪条线的第几页 |
| 条目数 | `item_count` | 这一页有多少条 |
| 时间区间 | `item_time_range` | **这一页是哪段时间** ← 找东西时的第一个问题 |
| 判定 · 体积 | `verdict` / `length` | 正常吗、多大 |

四条细节：

- **判定只在不是 `ok` 时显示。** 一整列「正常」是纯噪音，而那正好淹没了真正要看见的
  那几行。
- **`item_count` 的 `0` 与 `null` 显示得不一样。** `null` 是「这条路线没有条目概念」，
  `0` 是「数过了，是空的」——而空页正是翻页终点的正常形态，看到它说明这条线走完了。
- **两类时间绝不混用。** `item_time_range` 是内容覆盖的时间，`observed_at` 是抓取时刻。
  混起来的后果不是「不好看」：用户以为看到的是「第 7 页是 7 月中旬的广播」，实际看到的
  是「这一页是今天抓的」——后者在一次抓取里几十行几乎全一样，等于没有信息，还给出了一个
  错误的印象。
- **两种「没有内容时间」的措辞必须不同**（这一条是被报告出来的）：

  | 情形 | 怎么说 |
  |---|---|
  | 有内容时间 | `20 条 · 2026-07-12 → 2026-07-18`（只到天，秒是噪音） |
  | 这条路线本来没有（作品详情页） | `抓于 2026-07-30 20:43:16`（**精确到秒**） |
  | 旧档案，字段是后加的 | `抓于 … （这份档案没有记录内容时间）` |

  抓取时刻要精确到秒，理由与内容时间相反：一次抓取里几十行的**日期**全一样，只有秒能
  把它们区分开；既然这一行只剩这个信息可说，那就说得有用一点。

  而「我们当时没记」与「本来就没有」是两回事——把前者说成后者，等于替一份旧档案担保它
  其实没担保过的东西。

措辞逻辑在 `src/ui/capture-label.js`（纯函数，15 条测试）。**它原来埋在面板里，那时候
既没法测、也就没发现它在旧档案上退化成了「只显示抓取日期」。**

`item_count` 与 `item_time_range` 是为此加进规范的可选字段（bundle/v1 §6.1.2）。
抓取时本来就算过（判定要用），扔掉之后再想知道就得把记录取出来解压、再跑一遍
选择器——而豆瓣改版之后那些选择器可能已经对不上了。

### 10.2 「验一验」

预览页要有一个用户能自己按的按钮：顺着 `index.ndjson` 走，按 `offset`/`length`
把每条 WARC 记录取出来解压。

这条路径**就是规范承诺第三方能走的那条**——不信任何声明，直接去段文件里把
字节取出来。读得通，档案就是自洽的。它和规范仓库里的参考校验器同源，只是跑在
浏览器里、面向用户。

### 10.3 导出：这一步之前，档案不算用户的

OPFS 里的东西挂在扩展的来源下。卸载扩展、清站点数据、某些「一键清理」都能
把它一次性抹掉，而用户完全不会被问一句。所以档案页上要直说：**没导出之前
不算你的**。

三条规则：

**① 校验回读目的地，不回读源头。** 源头对不对不是问题所在——问题是字节有没有
真的落到用户的盘上。配额耗尽、U 盘拔了、写入被中断，全都只在目的地那一侧
看得见。而用户导完就会删掉 OPFS 那份，所以一次悄悄截断的导出等于唯一的副本
没了。

**② 结果分三档，不折成布尔。**

| 说法 | 什么时候 |
|---|---|
| 已导出并校验 | 回读过目的地，字节数与 manifest 里的 sha256 全部对上 |
| 已导出（只验了字节数） | 抓取还没收尾，没有 manifest，没有摘要可对 |
| 导出有问题 | 有文件对不上——明说「这一份别拿来当备份」 |

把第二档说成「已校验」，正是这个项目一直在躲的那种假安心。

**③ 目的地非空时先问。** 文件选择器里随手点中的可能是文档目录，同名即覆盖，
而覆盖掉的东西没有回收站。默认拒绝，把已有文件名摆给用户看再让他决定。

另外，档案页**不能只看当前抓取状态**：跑完之后 checkpoint 与指针都不再指向
那份档案，只看状态的话「跑完了」恰好等于「再也导不出来」。所以直接列 OPFS
目录，多份档案给一个下拉选择。

### 10.4 存储管理与删除

（在调试标签里，因为它现在主要是开发期在用；F-08d 正式化时移到自己的页面。）

列表本身是**只读**的，所以走面板自己的只读 Worker，不必把 offscreen 拉起来。
**删除是唯一的例外**——它经由 offscreen 那条唯一的写入路径，而且安全检查放在那边，
因为「现在在抓哪一份」这个知识只在那里。

四条规则：

**① 正在抓的那份绝不许删。** 删了它，写入器下一次落盘就会往一个不存在的目录里写，
而抓取正跑在几小时的中途。按钮灰掉的同时**把原因写出来**——灰掉的按钮看起来像 bug。

**② 确认框要说出「要失去的具体东西」。** 哪一份、多大、导出过没有。一句「确定删除
吗？」等于什么都没说。清空全部时逐条列出，并说明哪些会被保留。

**③ 界面上的确认框与代码里的守卫都要有。** 前者给人看，后者给代码守——用户可能点得
很快，而消息也可能是从别处发来的。

**④ 导出状态不知道就说不知道。**

| 显示 | 什么时候 |
|---|---|
| ✔ 已导出（时间） | 有本机记录，且那次导出**校验通过** |
| 未导出 —— 这是唯一的副本 | 没记录，且记录机制可用 |
| 不确定（本机没有导出记录） | 记录读不出来 |

第三档很重要：导出记录只在这台浏览器里，换过机器、清过数据、或者用别的方式导出过，
我们都看不见。这时显示「未导出」是在替用户下一个我们没资格下的判断。而在决定确认框
说得多重时，`unknown` **按最坏情况算**——不确定的时候要警告，不要放行。

「已导出」只在校验通过时才记：没验过就说已导出，等于给了一个我们没资格给的保证。

### 10.5 调试页（开发期）

自检页原本是个独立入口。把它并进面板的**调试**标签，理由不是省一个页面，而是
它和「验一验」验的是同一件事的两端：自检验的是**部件在这个浏览器里还能用**，
验一验验的是**写出来的档案自洽**。分在两处，就没人会两个都看。

三块内容：

**① 演练（零网络请求）。** 有几个场景**不能靠真实抓取来验证**——被风控拦截、
验证码、掉登录、账号被换。触发它们的唯一办法是真的去撞豆瓣的风控，而那正是这个
项目要不惜代价避免的事。所以给它们一条不碰豆瓣的路子：手写夹具喂进真实的分类器、
frontier、写入器、水位线，除了网络之外每一块都是生产代码。

每个剧本旁边印着一句「预期：……」。那句话是**断言**，不是说明文字——所以它在
`test/dry-run.test.js` 里逐条真跑一遍。一个说谎的调试工具比没有调试工具更糟：
夹具写歪了，演练会安安静静给出绿色结果，用户以为「拦截会被识别」已经验过了。

**②′ 作品详情页那一项会绕过抓取顺序。** 正常抓取里它要等广播跑完——广播可静默删除、
删了就再也拿不回来，而作品详情页随时能重抓，不能拿最不可替代的换最可替代的。但那条
路线占档案九成体积、在全量抓取里几小时之后才轮到，所以调试项显式跳过门控，用几十次
请求把它验完。**界面上必须把「绕过了什么」说出来**，不能只写在按钮说明里。

**② 小范围试跑（会真的访问豆瓣）。** 这里有一条必须说清的区别：

| | 怎么停的 | 算不算完成 | 水位线 |
|---|---|---|---|
| **自然终止** | 到达下界 / 翻完最后一页 / 停滞 | 算 | 推进 |
| **人为截断** | 撞上条数上限 | **不算** | **不推进** |

「只抓最近 7 天」是**自然终止**——它跟每一次增量抓取的正常形态一模一样，因此能
完整走完整个生命周期，包括干净完成与水位线推进。「最多 10 条」是**安全阀**，
被它砍断的抓取产出的是残缺档案，界面必须如实这么说。把安全阀当终止条件展示，
就是让用户以为「跑完了」。

同理，挑一条**天然就很小**的路线（真实档案里舞台剧只有一两条）也能走完全程，
而且不需要任何截断。

**③ 环境与存储自检。** OPFS、`CompressionStream`、File System Access 的可用性，
以及配额占用。不显示 `persist()`——它在扩展里恒为 `false`，是预期行为而非风险
信号（保护来自 `unlimitedStorage` 权限），摆出来只会制造假的不确定性。

调试标签是开发期工具，发布前决定是留、是藏在设置后面、还是删掉。

## 11. 明确不做的

- 抓取过程的实时页面预览（诱人，但会让人盯着看，且消耗资源）
- 把档案渲染成可浏览的站（那是 site-generator 的事，见 §10 的边界）
- 任何形式的账号/云同步（与项目立场冲突）
- 深色模式之外的主题定制

## 12. 实现顺序与现状

界面不阻塞写入器，但也不能拖到最后——没有界面就没法做真实抓取实测。这一点被反复验证：
这份文档里几乎每一条「不能这样说」的规则，都是先在真机上看到了才写下来的。

| 阶段 | 做什么 | 现状 |
|---|---|---|
| U1 | 显示状态、开始/暂停 | ✅ 起初做在 popup 里，后来 popup 整个拆掉（§1.1） |
| U2 | 主面板：概览 + 日志 | ✅ 日志已持久化（§3.4） |
| U3 | `awaiting_human` 全流程（§5） | ✅ 含通知与角标（§4.5） |
| U4 | 覆盖率页（§4）与存储页（§6） | 🟡 覆盖率 ✅；存储管理在调试标签里，还没独立成页 |
| U5 | 预览页与「验一验」（§10） | ✅ 含导出与回读校验（§10.3） |
| U6 | 首次使用说明、危险操作干预、文案打磨 | ⬜ 首次使用说明（§2）还没做 |

调试标签（§10.5）跟着 U2 走——真实抓取之前必须先能演练那几条撞不得的路径。

### 12.1 界面这边还欠的

| | 为什么要紧 |
|---|---|
| **首次使用说明**（§2） | 现在打开面板直接就是「开始抓取」，没有任何一句解释这个按钮会做什么、要多久、请求从哪里发出 |
| 存储页独立成页（§6） | 现在挤在调试标签里；`已用 / 未导出` 那个显眼的量（§6.1）还没做 |
| 增量抓取的界面 | 抓取本身就还没接上增量，界面上现在只是**如实说**「这次是全量」 |

### 12.2 这份文档里的规则，哪些是被真机打出来的

写下来是因为它们都不是提前想到的：

| 规则 | 起因 |
|---|---|
| §3.3.1 覆盖率只能有一个所有者 | 删掉档案之后覆盖率还显示着它的数字 |
| §3.3.2 要读档案的页面都得有加载态 | 覆盖率页第一次点进去是空白，看起来像在加载 |
| §4.3.1 「已回溯到」用最旧那条 | 抓了十页那个日期一动不动，被当成 bug 报过来 |
| §4.4 `active` ≠ 正在发请求 | 暂停之后界面还写着「正在抓取」，用户以为按钮坏了；继续那一侧更狠，直接让「继续」变成假按钮 |
| §4.4b 写出正在抓的 URL | 只有档案编号与间隔的话，界面几小时不变，看不出它在动还是卡住了 |
| §4.4c 空闲态进度表只归 `showLastRun()` 写 | 否则两秒后的轮询会把刚显示出来的上次结果抹掉 |
| §4.4d 「正在做什么」由后端报，不由界面编 | 确认账号那几秒会被轮询盖回「没有进行中的抓取」 |
| §4.4e 「已回溯到」用每页中位数 | 一条离群的旧条目会把全局最小值永久钉死，进度看起来卡住 |
| §4.4f 单独列出「已经没有了」的条目 | 最不可替代的信息，原来只是判定分布里的一个数字 |
| §4.5 通知只在状态变化时弹 | 同一条通知每 30 秒弹一次 |
| §10.1 捕获列表每行要有信息 | 列表长成一串「广播 正常 / 广播 正常」 |
| §3.4 日志要真的存下来 | 界面写着「仅本地保留…导出前请自行脱敏」，而它既没存也没有导出 |
